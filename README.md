## HEX → RGB → HSL 转换实现逻辑

采用标准数学公式，无近似值。

### HEX → RGB

将去掉 `#` 后的 6 位十六进制字符串解析为 24 位整数，再按位提取 R、G、B 三个通道：

```
r = (value >> 16) & 255
g = (value >> 8) & 255
b = value & 255
```

### RGB → HEX

每个通道转两位大写十六进制字符，拼接为 `#RRGGBB`：

```typescript
const toHex = (n: number) => n.toString(16).padStart(2, '0').toUpperCase()
return `#${toHex(r)}${toHex(g)}${toHex(b)}`
```

### RGB → HSL

1. 将 R、G、B 归一化为 `[0, 1]`。
2. 计算 `max` 与 `min`，得到明度 `L = (max + min) / 2`。
3. 若 `max === min`，则 `S = 0`（灰度）。
4. 否则 `S = max === min ? 0 : l > 0.5 ? d / (2 - max - min) : d / (max + min)`。
5. 根据 `max` 对应的通道计算色相 `H`，结果映射到 `0°–360°`。

### HSL → RGB

采用标准色相环插值算法：

1. 若 `S = 0`，则 `R = G = B = L`（灰度）。
2. 否则计算 `q = L < 0.5 ? L * (1 + S) : L + S - L * S`，`p = 2L - q`。
3. 对 `H + 1/3`、`H`、`H - 1/3` 分别调用 `hue2rgb` 插值函数，得到 R、G、B。

## 调色板生成规则

所有色相偏移均在 HSL 空间计算，超过 `360°` 时取模循环：`((h % 360) + 360) % 360`。

### 单色版（Monochrome）

- **核心规则**：5 种颜色**色相与输入色完全相同**，仅调整明度 `L`。
- **明度分布**：以输入色明度 `base.l` 为中心，向两侧均匀扩展，步长 `step = min((base.l - 5)/2, (95 - base.l)/2, 20)`。
- **生成值**：`base.l - 2·step`、`base.l - step`、`base.l`、`base.l + step`、`base.l + 2·step`，限制在 `[5, 95]`。
- **极端处理**：若 `step < 3`（如 `#000000`、`#FFFFFF`），采用固定均匀分布 `[5, 25, 50, 75, 95]`，并将最接近输入色明度的位置替换为实际值，确保 5 色可区分。
- **色彩协调保障**：色相严格一致，明度步长均匀，无扎堆无断层。

### 邻近色版（Analogous）

- **核心规则**：以输入色为中心，色相分别偏移 `-30°、-15°、0°、+15°、+30°`。
- **色彩协调保障**：严格限制在 `±30°` 范围内，输入色始终位于中心位置（0° 偏移）。
- **灰度处理**：若输入为纯灰色（`S = 0`），自动赋予低饱和度（`10%–50%`）并微调明度，避免生成不可区分的灰块。

### 互补色版（Complementary）

- **核心规则**：围绕输入色及其精确 `180°` 互补色生成 5 种颜色：
  1. 输入色（`base.h, base.s, base.l`）
  2. 浅输入色（`base.h, base.s, base.l + 15`，上限 90）
  3. 互补色（`base.h + 180°, base.s, base.l`）
  4. 浅互补色（`base.h + 180°, base.s, base.l + 15`，上限 90）
  5. 中性衍生色（`base.h, max(base.s - 40, 0), 50`）
- **色彩协调保障**：互补偏移精确 `180°`，非"大致相反"。
- **灰度处理**：纯灰色输入时自动赋予低饱和度并分配冷暖色相，确保 5 色可区分。

### 重复检测与确定性微调

若任意调色板生成过程中出现相同 HEX，对冲突颜色的明度进行确定性 `±2%` 微调（交替方向），最多尝试 10 次，确保每组 5 色全部唯一。

## 命名规则（覆盖 16,777,216 种颜色）

命名系统由代码**自动生成**，无人工对照表、无硬编码特例。

### 结构

`[明度词][饱和度词][色相词][后缀]`，共 4 个语义单元，长度符合 3–5 词要求。

### 词库划分

- **明度词（5）**：极暗、深沉、中等、柔和、浅淡
- **饱和度词（4）**：灰调、自然、鲜明、浓烈
- **色相词（24）**：每 `15°` 一个步长，覆盖 360° 色相环
  - 赤红、朱红、橙红、琥珀、金黄、柠黄、草绿、翠绿、薄荷、青绿、青色、天蓝、蔚蓝、宝蓝、靛蓝、紫罗兰、紫晶、品红、兰花、玫瑰、珊瑚、宝石红、猩红、绯红
- **后缀（40,000 种组合）**：由 200 个单字两两组合而成，如"霞光"、"暮霭"、"星辰"

### 唯一性与确定性

对每种颜色计算确定性哈希：

```
hash = (R << 16) | (G << 8) | B
```

然后依次取模索引：

```
明度索引   = hash % 5
饱和度索引 = floor(hash / 5) % 4
色相索引   = floor(hash / (5*4)) % 24
后缀索引   = floor(hash / (5*4*24))
```

**组合空间**：`5 × 4 × 24 × 40,000 = 19,200,000 > 16,777,216`，完全覆盖 24 位色彩空间，理论无冲突。

**确定性**：同一 RGB 值始终生成同一名称。

### 色相准确性

色相词完全由 HSL 色相值所在的 `15°` 区间决定，确保红色不会命名为"森林绿"。

### 灰度处理

纯灰色（`S = 0`）无定义色相，采用智能策略：
- 浅灰（`L > 50%`）赋予冷色调色相 `210°`（偏蓝）
- 深灰（`L ≤ 50%`）赋予暖色调色相 `30°`（偏橙）

确保灰色颜色也能获得有意义的名称，而非崩溃或命名失败。

## 预览作品说明

作品类型：**界面原型（UI Mockup）**

使用 SVG 渲染一个包含顶部导航栏、侧边菜单、内容卡片与统计小部件的仪表板界面。

**颜色分配**：
- `colors[0]` → 页面背景
- `colors[1]` → 导航栏与侧边栏
- `colors[2]` → 内容卡片
- `colors[3]` → 按钮与装饰圆环
- `colors[4]` → 文字与线条

**为何选择界面原型**：
- 调色板的核心用途之一即为 UI 设计，界面原型能最直接验证调色板的实际可用性。
- 五种颜色各司其职（背景、容器、强调、文字），任何颜色不协调都会立即暴露。
- 极限输入（`#FFFFFF`、`#000000`、纯灰色）下，通过 `opacity` 微调与确定性灰度处理，仍可渲染出可识别的界面结构。

## 已知实现局限

1. **HSL 感知亮度不均匀**：HSL 色彩空间的明度 `L` 与人眼实际感知亮度并非线性对应。例如黄色（`h=60°`）在相同 `L` 值下看起来比蓝色（`h=240°`）更亮。这可能导致某些调色板在视觉上不够均衡。
2. **命名可读性边界**：后缀由 200 个单字两两随机组合，虽然大部分组合通顺（如"霞光"、"暮霭"），但少数组合可能略显生硬。尚未引入语义搭配过滤。

## 时间充裕时的优化方向

1. **迁移至 OKLCH 色彩空间**：OKLCH 的明度 `L` 基于人眼感知均匀设计，可彻底解决 HSL 的亮度不均匀问题，生成真正视觉均衡的调色板。
2. **语义化后缀词库**：引入词性标注与搭配规则，确保后缀组合更具诗意与可读性，例如仅允许"形容词+名词"或"名词+名词"的合理搭配。
3. **URL 状态持久化**：将当前输入色编码到 URL 参数中，支持分享特定调色板链接。
